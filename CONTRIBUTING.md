# Contributing

Issues and pull requests are welcome. Security issues should not be raised as public issues: see [SECURITY.md](SECURITY.md).

Two things worth knowing before you start:

- **No PHPUnit.** The harness in `tests/unit.php` is deliberate rather than an oversight: no PHPUnit major spans PHP 7.4 to 8.5, so a suite built on one would only ever run on part of the supported range.
- **PHP 7.4 is the floor**, because Magento 2.4.2 ships it, and Composer 2.2 is the oldest supported. Both are in CI and neither is negotiable.

## Running the tests

```sh
composer install
php tests/unit.php                   # unit suites, about 20 seconds
php tests/unit.php collector         # one suite
vendor/bin/phpstan analyse           # level 8
tests/acceptance.sh                  # the whole matrix, real Magento in Docker
tests/acceptance.sh 2.4.8-p5-php8.4  # one image
```

`tests/unit.php` covers what can be reasoned about without a Magento install: splitting a patch into fragments, resolving root-mapped and linked paths, the end-of-life dates, exit codes, and, with `composer/composer` installed, how patches from every source are collected, ordered and applied. Without Composer's own classes the collector suites are skipped and say so.

`tests/acceptance.sh` drives real Magento installations in the `samjuk/magento-ci-testing-env` images and asserts on what ends up on disk: self-heal after a package reinstall, both copies of root-mapped files, symlink and hardlink deploy strategies, replaced-away modules, chain refusal and cascade, supersede, conflicts left untouched, and every exit code.

Fixtures are generated by `tests/fixtures/build.php` from the files actually present in whichever Magento the image contains. They are real diffs against real vendor files, and they depend on nothing outside this repository: no other package has to be published, or unchanged, for these tests to mean anything.
